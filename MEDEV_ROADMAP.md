# MeDev — Roadmap к боевому уровню
> Написан после анализа реального кода (backend + frontend).  
> Каждая фаза — конкретные задачи, не абстракции.

---

## Фаза 1 — Данные: GitHub как единственный источник правды
**Цель:** профиль заполняется сам, без ручного ввода.

**Проблема в коде сейчас:**
- `GitHubService.languageStats` считает по кол-ву репозиториев, а не по байтам кода. Java с 1 большим репо проигрывает HTML с 5 маленькими.
- `fetchUserPublicRepos` тянет только 10 репо без авторизации — теряем приватные проекты и реальную статистику.
- `importToProfile` не вытаскивает из README технологии, даты, описания.

**Что делаем:**
- GitHub API: для каждого репо вызывать `/repos/{owner}/{repo}/languages` — получаем байты, не счётчик.
- README парсинг: вытаскивать tech stack через регулярки / LLM из README каждого выбранного репо.
- Даты коммитов как прокси опыта: первый коммит на Java = "работает с Java с 2022".
- Организации: `/user/orgs` → company field в Experience.
- Хранить raw GitHub snapshot в отдельной таблице `github_snapshots` с `fetched_at` — чтобы всегда знать свежесть данных.

**Результат:** пользователь коннектит GitHub — профиль заполнен на 70% автоматически.

## Фаза 2 — Smart Merge: AI генерирует весь профиль, не только summary
**Цель:** `AiGenerateService` генерирует experience, education, skills, projects — всё.

**Проблема в коде сейчас:**
- `generateSummary` и `generateProjectDescription` — только два метода. Всё остальное пользователь вводит руками.
- `resume_parser_v1.txt` — хороший промпт, но вызывается только при загрузке PDF. Без PDF — ничего не генерируется.
- `onboarding_wizard_v1.txt` генерирует experience с `company: "Recent Company"` — заглушка, не реальные данные.

**Что делаем:**
- Новый промпт `full_profile_generator_v1.txt`: принимает GitHub snapshot + онбординг-ответы → генерирует полный профиль.
- Источники данных в промпте помечены явно:
  ```
  [SOURCE: GitHub — считать актуальным]
  [SOURCE: PDF — использовать для опыта/образования]
  [SOURCE: User input — доверять как есть]
  ```
- `AiAnalysisService.parseResumePdf()` получает третий аргумент: `GitHubProfileDto freshGithubData` — свежие данные с GitHub, не из кэша профиля.
- Правило: GitHub = источник правды для языков/проектов/стека. PDF = источник правды для дат, компании, образования.
- Запрет: если данных нет ни в одном источнике — поле остаётся `null`. Никакой галлюцинации.

**Результат:** после подключения GitHub + загрузки PDF профиль заполнен на 95%. Руками — только то, чего нет нигде.

## Фаза 3 — PDF: профессиональные шаблоны
**Цель:** резюме выглядит лучше, чем у конкурентов (HH.kz, Canva).

**Проблема в коде сейчас:**
- `PdfGeneratorService` использует Thymeleaf + Flying Saucer (ITextRenderer). Это генерация HTML → PDF. Контроль над дизайном ограничен CSS.
- Есть `ClassicTemplate.tsx` и `ModernTemplate.tsx` на фронте — но они для превью, не для финального PDF.
- Шрифты, отступы, цвета — скорее всего дефолтные.

**Что делаем:**
- 3 шаблона минимум: Classic (строгий, для корпораций), Modern (с акцентами, для стартапов), Compact (одна страница, для джунов).
- Каждый шаблон — отдельный Thymeleaf `.html` файл с встроенными CSS-переменными для цветовой схемы.
- Шрифты через base64 embed в CSS (не зависеть от системных шрифтов при генерации).
- Проверка одностраничности: если контент не влезает — автоматически уменьшать `font-size` и `line-height`, не рвать на две страницы.
- Фронт: превью в реальном времени через React-to-PDF или iframe с HTML — то, что пользователь видит = то, что скачивает.

**Результат:** PDF, который не стыдно отправить в Google.

## Фаза 4 — Job Tracker: киллер-фича
**Цель:** трекер вакансий с AI-автоматизацией — главное отличие от всех конкурентов.

**Что уже есть:**
- `JobApplicationController`, `JobApplicationService`, `ApplicationStatus` — структура есть.
- `AiApplicationService` — есть, но нужно смотреть что именно делает.

**Что добавляем:**
- Парсинг вакансии по URL: пользователь вставляет ссылку на вакансию → `WebScraperService` (он уже есть!) вытаскивает требования, стек, компанию.
- AI-матчинг: сравниваем требования вакансии с профилем → score совпадения + список gap'ов.
- Одним кликом: "Адаптировать резюме под эту вакансию" → AI перепишет summary и переставит акценты в skills под конкретный JD.
- Статусы: Applied → Phone Screen → Technical → Offer / Rejected. Дата каждого перехода.
- Канбан-вид на фронте (уже есть `JobTrackerPage.tsx` — нужно доделать).

**Результат:** пользователь управляет всем поиском работы из одного места. Это то, чего нет у Resume.io.

## Фаза 5 — Portfolio Page: публичная витрина
**Цель:** `app.com/username` — страница, которой не стыдно поделиться в LinkedIn.

**Что уже есть:**
- `PortfolioController`, `PortfolioService`, `PortfolioPage.tsx`, `PortfolioView.tsx` — структура есть.
- `PublicProfileDto` — DTO для публичного профиля.

**Что улучшаем:**
- SEO: meta теги, og:image, structured data (JSON-LD для Person schema) — чтобы Google индексировал.
- GitHub Activity Graph: виджет активности (как на GitHub профиле) — через GraphQL stats, которые уже тянем.
- Проекты с превью: если есть `githubUrl` → через GitHub API подгружаем stars, last commit, языки.
- Кастомизация: пользователь выбирает какие секции показывать и в каком порядке (drag-and-drop уже в планах).
- Публичная ссылка: `medev.app/орынбасар` — красивый slug, не UUID.

**Результат:** страница, которую разработчик ставит вместо LinkedIn.

## Фаза 6 — UX и полировка интерфейса
**Цель:** продукт ощущается как Notion или Linear, не как студенческий пет-проект.

**Что делаем:**

**Onboarding:**
- Сейчас онбординг спрашивает Role/Stack/Experience текстом. Нужен визард: шаг 1 — подключи GitHub, шаг 2 — загрузи PDF (опционально), шаг 3 — проверь и подтверди.
- Progress bar, анимация заполнения профиля — пользователь видит как профиль "оживает".

**Profile Editor:**
- Inline редактирование: кликнул на поле → редактируешь прямо там, без модалки.
- AI-кнопки рядом с каждым полем: "Улучшить с AI" → `generateSummary` / `generateProjectDescription`.
- Drag-and-drop порядка секций (ReorderRequest уже есть в коде).

**Общее:**
- Skeleton loaders везде где есть async запросы.
- Optimistic updates через React Query — UI обновляется сразу, не ждёт сервер.
- Toast-уведомления единого стиля для всех операций.
- Пустые состояния с CTA: "Нет опыта работы — добавить вручную или импортировать из GitHub".

## Фаза 7 — Безопасность и надёжность
**Цель:** то, что уже знаешь как проблему — исправить до деплоя.

**Что делаем:**

**Auth:**
- JWT refresh rotation: при каждом refresh → новый refresh token, старый инвалидируется. Хранить в HttpOnly cookie, не в localStorage.
- `EncryptedStringConverter` и `StringCryptoConverter` — два одинаковых класса, выбрать один, удалить дубль.
- GitHub access token в БД — шифруется через `EncryptionUtils` (уже есть), проверить что везде используется.

**Rate Limiting:**
- `RateLimitFilter` и `AuthRateLimiter` — убедиться что покрывают все AI-эндпоинты, не только auth.
- AI эндпоинты: лимит по userId, не по IP (один юзер = один лимит, VPN не обходит).

**Входные данные:**
- PDF upload: проверка mime type на сервере (не только по расширению), лимит размера файла.
- GitHub username в URL: санитизация перед запросом к GitHub API.

**Мониторинг:**
- `AuditService` уже есть — убедиться что логирует все AI-вызовы с userId, токенами, статусом.
- Health endpoint с проверкой Redis, DB, Groq доступности.

## Фаза 8 — README Generator и экспорты
**Цель:** закрыть все форматы экспорта, README как отдельная killer-фича.

**Что уже есть:**
- `ReadmeGeneratorService` — есть.
- `ReadmeGeneratorServiceTest` — есть.

**Что улучшаем:**

**README Generator:**
- Шаблоны: Minimal (только проекты и стек), Full (с badges, stats, контактами), Creative (с ASCII-артом и нестандартной структурой).
- GitHub Stats badges: автоматически генерировать ссылки на `github-readme-stats` с параметрами из профиля.
- Preview прямо на сайте: рендер Markdown в реальном времени.
- Инструкция "Как вставить": конкретные шаги для GitHub profile README.

**Дополнительные экспорты:**
- JSON экспорт профиля (для API интеграций в будущем).
- LinkedIn-ready текст: адаптированный summary и experience в формат LinkedIn About + позиции.

**Мультиязычность:**
- Генерация резюме на EN/RU по выбору — промпты уже поддерживают `language` параметр, нужно добавить в UI.
- i18n уже подключен (`en.json`, `ru.json`) — убедиться что все новые строки переведены.

## Итоговый порядок работ

```
Фаза 1 (GitHub данные)     → Фаза 2 (Smart Merge AI)
         ↓                              ↓
Фаза 3 (PDF шаблоны)       → Фаза 4 (Job Tracker)
         ↓                              ↓
Фаза 5 (Portfolio page)    → Фаза 6 (UX полировка)
         ↓
Фаза 7 (Security)          → Фаза 8 (README + экспорты)
```

**Правило:** фазы 1 и 2 — блокирующие. Без нормальных данных и AI-генерации всё остальное теряет смысл.  
Фазы 3-6 можно делать параллельно.  
Фазы 7-8 — перед публичным запуском.
