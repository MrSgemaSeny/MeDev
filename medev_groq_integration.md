# Интеграция GROQ в MeDev — архитектура

## Контекст

Три сценария использования LLM в MeDev:
1. Анализ — разбор данных резюме (PDF-парсинг + GitHub-данные) в структурированный профиль
2. Генерация текстов — описания для портфолио-страницы, буллеты опыта, summary
3. AI-ассистент — интерактивный чат-помощник

Все три упираются в один вопрос: где живёт вызов к GROQ и как это сочетается со стеком (Spring Boot + PostgreSQL + Redis + React).

## Где размещать интеграцию

[CRITICAL] Ключ GROQ_API_KEY никогда не должен попадать во фронтенд — ни в бандл, ни в публичный env. Значит все три сценария идут через бэкенд как прокси, а не прямой вызов из React. Это не обсуждается, это следует из твоего же определения production-ready (секреты в env, не в клиенте).

Отдельный модуль `ai` в бэкенде (по аналогии с `auth`, `profile`):
- `AiClient` — тонкая обёртка над GROQ REST API (OpenAI-совместимый эндпоинт `/openai/v1/chat/completions`)
- `AiAssistantService` — бизнес-логика поверх клиента: сборка промпта, обработка ответа
- Три разных use case — не три разных клиента. Один `AiClient`, три метода/сервиса поверх него (`ResumeAnalysisService`, `TextGenerationService`, `AssistantChatService`), потому что клиент — это транспорт, а логика промптов у каждого своя.

## Синхронный вызов vs стриминг

GROQ отдаёт то и другое.

- Анализ резюме и генерация текста — синхронный вызов достаточен, ответ короткий, пользователь ждёт секунды
- Чат-ассистент — стриминг обязателен по UX (иначе пользователь смотрит на спиннер 3-5 секунд на длинный ответ). Реализуется через SSE (Server-Sent Events), не WebSocket — тебе не нужен full-duplex, только сервер→клиент поток токенов. SSE проще в Spring (`SseEmitter`) и не требует STOMP-инфраструктуры, которую ты используешь в JF-1C для другого случая (двусторонний чат между людьми — там WebSocket оправдан, здесь нет)

## Rate limiting

У GROQ free tier жёсткие лимиты по токенам в минуту (плавающие, зависят от модели). Два уровня защиты нужны одновременно:
- Bucket4j на твоих собственных AI-эндпоинтах — защита от твоих же пользователей, гасящих квоту (ты уже используешь Bucket4j в JF-1C на auth, паттерн переносится)
- Обработка 429 от самого GROQ — retry с backoff на 1-2 попытки, дальше явная ошибка клиенту, не бесконечный retry

[WARNING] Free/Pro монетизация, которую ты уже заложил в MeDev, естественно ложится сюда: лимит AI-запросов в день/месяц для Free, выше или без лимита для Pro. Если не заложишь это на уровне архитектуры сейчас (отдельная таблица usage или счётчик в Redis на user_id), потом придётся встраивать rate limiting задним числом в уже работающий модуль — дороже.

## Безопасность промпта

Резюме и данные из GitHub — контент, загруженный пользователем, то есть untrusted input, который ты вставляешь в промпт. Риск prompt injection низкий (это не публичный чат с произвольными данными третьих лиц), но:
- Не давай LLM инструменты/function calling с доступом к БД или файловой системе на основе контента резюме
- Ограничивай длину входного текста перед отправкой (защита от case, когда PDF содержит мусор на десятки страниц — это и стоимость, и риск)

## Кеширование

Redis у тебя уже в стеке. Анализ одного и того же резюме/GitHub-профиля без изменений — кандидат на кеш (ключ — хеш входных данных), особенно если пользователь несколько раз открывает конструктор и триггерит повторный анализ без правок. Для чат-ассистента кеш не имеет смысла (диалог уникален).

## Что не проектировать сейчас (future consideration)

- Мультипровайдерность (fallback на другой LLM-провайдер, если GROQ недоступен) — при 0-100 пользователях избыточно, добавишь если станет проблемой
- Векторный поиск/RAG по базе резюме — не нужен для трёх заявленных сценариев

## Открытый вопрос

Чат-ассистент — это ассистент по заполнению профиля (контекст = данные пользователя в системе) или общий чат без контекста? Это определяет, нужен ли системный промпт с инжектом текущих данных профиля при каждом запросе, или это независимый чат.
