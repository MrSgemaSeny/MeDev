# Теория дизайна для продуктовых веб-приложений

## Главный принцип

Дизайн — это снижение когнитивной нагрузки. Пользователь не читает страницу — он сканирует. Метрика качества не эстетика, а **Time to Value**: как быстро пользователь нашёл → понял → сделал.

---

## 1. Визуальная иерархия

Один экран — одно главное действие. Всё остальное подчинено ему.

Иерархия строится через четыре инструмента:

- **Size** — крупное читается первым
- **Weight** — bold только для реально важного
- **Color** — акцент максимум на 1–2 элементах одновременно
- **Space** — пустое пространство повышает вес соседних элементов

Ошибка: всё одинаково важно → всё одинаково незаметно.

---

## 2. Система токенов

Хаотичные решения "по ощущению" не масштабируются. Нужна система.

### Spacing — шкала 4px grid
```
4 / 8 / 12 / 16 / 24 / 32 / 48 / 64px
```
Никаких `margin: 13px`. Любое значение вне шкалы — красный флаг.

### Typography — максимум 4–5 размеров
```
11px  — labels, captions (uppercase + letter-spacing)
13px  — body, inputs, nav
14px  — secondary headings
17px  — page titles
22px+ — display (только landing)
```
Максимум 2 шрифта. 2–3 веса: 400 / 500 / (600 только при необходимости).

### Color tokens
```
background:   #0f0f0f   — канвас
surface:      #1a1a1a   — карточки, поля
border:       rgba(255,255,255,0.08)
text-primary: #f0f0f0
text-muted:   #6b7280
accent:       один цвет  — не пять
danger:       #ef4444
success:      #22c55e
```

### Component states — обязательно для каждого интерактивного элемента
```
default → hover → focus → disabled → error
```
Отсутствие любого из состояний = сломанный UX.

---

## 3. Формы

Форма — это диалог, не анкета.

| Правило | Почему |
|---|---|
| Label всегда над полем | Placeholder исчезает при вводе |
| Группируй логически | Снижает когнитивную нагрузку |
| Inline validation | Ошибка сразу при blur, не после submit |
| Одна колонка > две | Меньше скачков взглядом |
| Primary action слева | Европейский порядок чтения |

---

## 4. Навигация

Максимум 2 уровня вложенности для dashboard-приложений.

```
ХОРОШО:                    ПЛОХО:
sidebar → content          sidebar → sections → content
```

GitHub Settings, Linear, Vercel — все используют один sidebar. Этого достаточно для любого объёма данных.

---

## 5. Пустые состояния (Empty States)

Пустой экран без empty state читается как баг.

Структура:
```
[иконка]
Заголовок — что здесь будет
Одна строка — зачем это нужно
[CTA кнопка]
```

Пустое состояние — это онбординг, не ошибка.

---

## 6. Плотность контента

Контент должен помещаться на экране без скролла там, где это возможно. Скролл допустим только для списков и длинного контента (документы, логи). Формы, настройки, dashboard-панели — без скролла.

Инструменты для уплотнения:
- 3-колоночная сетка вместо 2-колоночной для коротких полей
- Убрать избыточные section-dividers
- Textarea ограничить `rows` вместо `min-height`
- Группировать связанные поля в одну строку

---

## 7. Что отличает production-уровень

| Признак | Junior | Production |
|---|---|---|
| Spacing | произвольный | 4px grid |
| Цвет | много акцентов | 1 акцент + токены |
| States | только default | все 5 состояний |
| Empty states | отсутствуют | онбординг |
| Типографика | 8+ размеров | 4–5 по шкале |
| Анимации | нет или избыточно | 150–200ms, subtle |
| Иконки | разные наборы | одна система |
| Навигация | 3+ уровня | максимум 2 |
| Скролл | везде | только где нужен |

---

## 8. Анимации

Используются только там, где добавляют смысл:
- Переход между состояниями кнопки: 100–150ms ease-out
- Появление dropdown/modal: 150–200ms
- Hover на nav items: 100ms

Больше анимаций ≠ лучше. Избыточная анимация = ощущение "сделано AI".
